1. **`src/components/video-editor/clipSequence.ts`**: new `planTimeRangeDeletion()` — splits at both cut boundaries (a plain split moves nothing, so no ripple needed for that step), drops whatever's fully inside the cut, repacks the rest via the existing `packClipSequence`. 2. **`src/components/video-editor/transcriptEditing.ts`** (new): `planTranscriptWordDeletion()` removes a word-range selection from captions (a cue that loses all its words is dropped; one that loses some is shrunk to its remaining words' span) and reports the exact time span removed; `deleteTranscriptWordRange()` composes that with `planTimeRangeDeletion` + `rippleRegions` into the full atomic operation — cut the transcript, cut the timeline, ripple captions/zoom/annotations/audio, all from one call. `detectFillerWords()` (deliberately restricted to unambiguous fillers — um/uh/erm/hmm/huh — since "so"/"like"/"actually" are real words too often to flag without actual language understanding) and `detectRepeatedPhrases()` (within-cue false-start/stutter detection, longest-match-first) round out the 4B checklist. 15 new tests.

Threaded through `useEditorSettingsPanelProps.ts` → `VideoEditor.tsx` → `SettingsPanel.tsx`.
4. **`src/components/video-editor/TranscriptPanel.tsx`** (new UI): a scrollable flattened word list across every cue; click selects a word, shift-click extends the selection (in document order, across cue boundaries); filler words highlighted amber, detected repeated phrases underlined orange with a one-click "Remove repeat" action (removes the earlier/stuttered occurrence); a "Delete & ripple" button for the current selection. ## Instant Replay: verified live, real bug found and fixed (this session)
Built the real signed app specifically to test this. First attempt: pre-enabled Instant Replay via the settings file, launched, and watched the background ffmpeg process run for 30+ seconds with the chunk file frozen at a fixed size - segments were never rotating. Root-caused by testing the app's own existing (already-shipped, untouched) avfoundation capture command directly: this environment's avfoundation screen input reports a broken/nonsensical timebase (`1000000 tbr`). The existing single-file capture tolerates this fine, but the segment muxer's `-segment_time`-based cutting depends on real presentation timestamps ever crossing each threshold, which apparently never happened. **Fix**: added `-r 30` (a forced constant output frame rate, independent of the input device's timestamp reporting) to the segment muxer's ffmpeg args. Confirmed directly by running the exact command with and without the flag. Added a regression test locking in the specific flag. Rebuilt, relaunched, and confirmed: chunks now rotate correctly on schedule, and pressing the actual global shortcut (`Cmd+Shift+R`, sent via a real keystroke, not a coordinate click) produced a real, valid, playable 16.7-second `replay-*.mp4` file in the recordings directory.
**Lesson worth repeating**: 20 unit tests (15 pure-logic + 5 using real ffmpeg concat) were all green before this fix, and none of them would have caught it, because concat correctness was never the broken part — segment generation was. Pure-logic and even "real ffmpeg" tests that don't exercise the actual continuous capture command end-to-end can still miss a real bug in that specific command. When a feature's correctness depends on a specific long-running process behaving right, run that exact process for real before calling it done.
Also discovered and worked around during this: this app has a single-instance lock, so `osascript quit` + relaunch during testing can silently no-op if the quit doesn't fully land — a stale process from an EARLIER test kept running for over an hour before I noticed via `ps aux` that the PID hadn't changed across "quits." `pkill -9 -f "Screenly.app"` is the reliable way to fully clear it between test iterations.

## Inline retake-recording: built and verified (this session)
Went with option 2 from the earlier scoping note (screen capture stays HUD-only; the editor window coordinates with it instead of gaining direct capture access) rather than relaxing the `shouldGrantDisplayCapture` security boundary. Design: `showRecordingHud` (already used by the dashboard's "Record New" button) now accepts an optional `retakeClipId`; the main process remembers `{clipId, returnWindowId}`; when the recording stops, a new `finish-retake-recording` handler shows/focuses the *same* editor window **without reloading it** (the normal flow reloads and intentionally flushes the previous project - retake must not do that) and delivers the finished video path via an event, which the editor's existing `useClipRetake` hook feeds into the same `retakeClip` logic already used by the file-picker path.

**Verified for real**, via Chrome DevTools Protocol against the actual built app (`--remote-debugging-port` + `--remote-allow-origins=*`, not coordinate clicks) rather than left as "typechecks but untested" like the earlier commit worried it might be:
1. Opened the real editor window, set a JS marker and registered the real `onRetakeRecordingReady` listener in its context.
2. Called `showRecordingHud('test-clip-123')` from that window; confirmed via a *separate* window's context that `getPendingRetake()` returned `{clipId: "test-clip-123"}` - proving this is genuine shared main-process state, not per-window.
3. Called `finishRetakeRecording('/tmp/fake-retake-video.mp4')` (simulating a finished recording) from the HUD's context; got `{success: true}` back and confirmed `getPendingRetake()` was cleared afterward.
4. Back in the editor window: the marker set in step 1 was **still present** (proves the window was not reloaded) and `onRetakeRecordingReady`'s listener **had fired with exactly `{clipId: "test-clip-123", videoPath: "/tmp/fake-retake-video.mp4"}`**.
This confirms every genuinely novel/risky part of this feature (window-by-id lookup, no-reload show/focus, cross-window event delivery, shared pendingRetake state) works correctly end-to-end. The one thing not exercised in this specific test is `retakeClip` actually applying to a real clip in a real project (no clip with id "test-clip-123" existed) - that logic itself already has 10 passing unit tests in `retake.test.ts` and is unchanged by this session's work, so this was a deliberate, reasonable scope boundary for the test, not a gap.
**Reusable technique for future sessions**: CDP-based verification (launch with `--remote-debugging-port=N --remote-allow-origins=*`, `curl localhost:N/json` to list window targets, WebSocket + `Runtime.evaluate` to call `window.electronAPI.*` directly in a specific window's context) is safe, precise, and far more reliable than coordinate-click GUI automation for verifying IPC/cross-window logic - no risk of clicking the wrong window, and you can assert on exact state/event payloads instead of just eyeballing a screenshot. Prefer it over coordinate clicks whenever the thing being tested is reachable through `window.electronAPI` rather than requiring actual mouse/keyboard interaction with rendered UI.
