## Decisions

### Icon/logo — corrected to match the real reference (this session)
**What happened**: the app icon was originally hand-built in Phase 1 as an SVG *approximation* of the brand guideline's text description, because the brand-kit folder had no clean vector export at the time. The operator later supplied real reference images (the actual logo mark + a full brand-guidelines sheet). Comparing them, the original icon was structurally wrong — a thin, calligraphic stroke-based "S," when the real mark is built from **two thick, overlapping rounded-rectangle "ribbon" bars** with a flat diagonal crossing (chunkier, more geometric, per the guideline's own "Logo Construction" section: "S Ribbon," "Gradient," "Record Dot").
**Fix**: rebuilt `branding/source-assets/Screenly.svg` using two rotated `<rect rx="...">` capsule shapes with a shared 5-stop gradient (cyan→blue→violet→magenta→amber) plus a separate radial-gradient dot. Iterated 3 times, rendering each attempt via `qlmanage -t` and visually comparing against the reference before settling. Regenerated the full icon set (all PNG sizes, `.icns`, `.ico`) from the corrected SVG — see the exact pipeline in `02_ARCHITECTURE.md`.
**If it still doesn't look right**: the ideal fix is the operator's actual vector export (Figma/Illustrator SVG) dropped directly into `branding/source-assets/`, which would be pixel-perfect where a hand-built recreation from a raster reference can only be a close approximation. Ask before spending more iteration cycles on hand-tracing it further.

### Local LLM: Gemma 4 E4B via `@electron/llm` — chosen after real research, not guessed
**Constraint**: the operator explicitly required "whatever LLM you download must be the latest available as of today" — this ruled out picking from training-data memory (which predates "today" in this project's timeline) and required live web research to confirm the model actually exists, is current, and has a real, verifiable download location.
**Process**: searched for "best small local LLM 2026," found Gemma 4 (Google DeepMind, released April 2026, Apache-2.0, sizes E2B/E4B/26B-MoE/31B-Dense) — this matches the *original PRD's own* speculative "Gemma 4 E4B evaluation" line item, confirming the PRD's authors had accurate foresight. Found the GGUF conversion at the official `ggml-org` Hugging Face org (same maintainers as whisper.cpp — a trust signal, not just "some rando's GGUF repo"). **Verified the exact download URL resolves (HTTP 302 to real content) and pulled the exact SHA-256 from the HF API's file-tree endpoint before ever writing it into code** — the checksum in `electron/ipc/constants.ts` (`GEMMA4_E4B_MODEL_SHA256`) is not guessed, it's the real LFS object hash from Hugging Face's own metadata, and was independently re-verified by downloading the 4.6 GB file and running `shasum -a 256` on it, which matched exactly.
**Why Q4_0 quantization specifically**: reasonable size/quality tradeoff (~4.3 GiB vs. ~14 GiB for BF16), the standard "safe default" quant tier, and it's what `ggml-org`'s own repo lists as one of the smaller/most commonly used variants for CPU inference.
**Why `@electron/llm` over raw `node-llama-cpp`**: it's an *official Electron-org* package (not a random community wrapper), and its whole purpose is running the model in an Electron **utility process** with Mojo IPC streaming — exactly satisfying the PRD's "AI must not block the recorder" / "background worker" requirement, without me having to hand-build that process-isolation architecture myself. It's marked "Experimental" by its own maintainers — acceptable risk because our own code only ever touches it through one narrow, swappable wrapper (`src/lib/ai/localModelProvider.ts`); if `@electron/llm` needs replacing later, only that one file changes.

### Every AI feature must have an honest fallback story — not all features get the same kind of fallback
Three features were built (chapters, title, summary) specifically to cover three DIFFERENT points on the PRD's fallback hierarchy, deliberately:
- **Chapters**: model unavailable → real deterministic heuristic (pause-based segmentation, already existed from Phase 4A work) — a genuinely useful fallback, not a token gesture.
- **Title**: model unavailable → a weaker but honest deterministic proxy (opening words of the transcript).
- **Summary**: model unavailable → **no fallback at all**, reports "unavailable." This was a deliberate choice, not a gap: there is no honest deterministic algorithm that produces a real summary of arbitrary content. Faking one (e.g., "here's the first 3 sentences") would be presenting a non-summary as a summary, which is worse than admitting the feature needs the model. **Do not add a fake heuristic summary later just to "complete" the feature** — if a heuristic ever gets added here, it must be a real algorithm (e.g., extractive summarization via sentence-importance scoring), not a truncation dressed up as one.

### VoiceStudio (github.com/debpalash/VoiceStudio) — researched, deliberately NOT vendored
The operator asked me to evaluate this specific repo and "use your brain and decide." Findings: real, popular (40.8k stars), actively maintained, AGPL-3.0 (license-compatible with Screenly). But it is **a whole separate Electron application** with a Python backend and a Rust/Cargo + Bun build toolchain — not a library. Decision: do not vendor/embed its source. Reasons: (1) it would mean bundling an entirely different language runtime and build system alongside Screenly's existing Swift/C++/Node stack, disproportionate for "one feature"; (2) the alternative — calling a separately-installed VoiceStudio instance via its documented local API — would require the end user to install and run a second, unrelated desktop app just to get voiceover inside Screenly, a materially worse product experience than a self-contained feature; (3) conflicts with the general "keep the dependency footprint small" principle. **What WAS taken from it**: its default engine name (`k2-fsa/OmniVoice`) is now a known reference point for a possible *future* voice-cloning tier, and its existence as a mature, popular local-voice project is useful prior art if voice cloning specifically (not just narration) becomes a real priority later. This is a decision the operator should feel free to override if they weigh the tradeoffs differently — it's a judgment call, not a hard constraint.

### Voiceover engine: `kokoro-js` — the actual chosen path (not yet implemented)
Real, verified on npm (`kokoro-js@1.2.1`, Apache-2.0, maintained by the well-known Transformers.js/Xenova ecosystem author, only 2 dependencies — `@huggingface/transformers` and `phonemizer`). Runs Kokoro-82M **100% locally via ONNX** — no Python subprocess, no extra runtime bundling, just `npm install kokoro-js`. Reference Electron integration prior art exists at `davealaw/kokoro-electron` and `gooidtto/domekokoro-electron` on GitHub (both real, working, MIT-style open projects demonstrating the exact Electron+kokoro-js pattern to follow). This keeps the same low-dependency-footprint philosophy as the Gemma integration. **Not yet implemented** — see Next Steps.

### Why the transcript-editor UI bug (wrong `SettingsPanel.tsx` section) matters as a lesson, not just a fixed bug
It typechecked cleanly, passed lint, and every unit test for the underlying logic passed — and the feature still silently didn't render, because of a near-duplicate variable name (`captionSectionContent` vs `captionsSectionContent`) that no automated check could catch. **The lesson generalized**: for any UI feature, a live click-through of the actual running app is not optional polish on top of passing tests — it is the only check that catches "wired to the wrong place" bugs, which automated checks are structurally blind to. Budget time for it on every UI-facing change, not just at the end of a phase.

### Design redesign scope — sequenced deliberately, not attempted all-at-once
The operator's design-redesign directive is enormous (full IA rewrite + material system + ≥20 licensed/original wallpapers + every app surface + visual QA). Explicit decision: treat this as its own dedicated, multi-session body of work, sequenced *after* finishing the in-flight AI feature verification, rather than fragmenting effort across AI-verification + voiceover + full redesign simultaneously. This is a pacing choice the operator agreed with when raised, not a unilateral deprioritization — if the operator wants the redesign prioritized ahead of AI/voiceover work, say so explicitly and re-sequence.
